Yatra Pulse: design decision walkthrough

Everything you need to present this project and defend its design: the abstract, a 30-second and a 2-minute pitch, the architecture in five steps, every major decision with alternatives and trade-offs, real debugging stories, practice questions with model answers, and the numbers to quote.

01

Title, abstract and summary

Title

Yatra Pulse: Grounded, Feasibility-Checked AI Trip Planning for Festival Travel

Abstract

Festival travellers face dense, fast-changing schedules spread across venues kilometres apart, and generic AI assistants will happily invent events or propose plans that can't be followed. Yatra Pulse is a live travel board for Mysuru Dasara 2026 that combines a source-linked event schedule with a grounded AI planning agent. Every event, day trip and booking fact becomes a cited passage; a BM25 retriever selects the passages that match a traveller's style and dates; Claude drafts a day-by-day plan restricted to those passages; and a deterministic trip checker rejects nothing silently but flags clashes between venues, legs that can't be travelled in time by car, two-wheeler, auto-rickshaw or bus, gate deadlines and vehicle range. The same retrieval and checking code is exposed to Claude Code and Claude Desktop through a Model Context Protocol (MCP) server. Quality is enforced by an evaluator with labelled datasets (retrieval hit@1 0.97, recall@3 1.00, trip-check and plan-grounding accuracy 100%) gated in CI; every tool call is traced to Apache Pulsar, where a metrics consumer computes SLOs and raises alerts; and the system deploys as three Knative services on any Kubernetes cluster, verified end to end on kind with scale-to-zero and a 2.2 s cold start.

Summary
  • Product: 21 use cases: live schedule, filters, picks, itinerary, trip check, AI planner, booking guide, host-approved traveller events, day trips, Gaya panel; dark mode and phone.
  • AI: one agent goal ("a plan a traveller can actually follow"), RAG over 37 passages, key whitelist, trip check on every draft, tips only from retrieved facts.
  • Interfaces: claude.ai artifact, GitHub Pages, MCP over stdio and Streamable HTTP.
  • Quality: 16 Selenium checks, 8 MCP protocol checks, evaluator with 45 labelled cases, CI gates.
  • Operations: Pulsar telemetry with file fallback, Prometheus metrics, 4 SLOs, alerts, DLQ, runbook, game day.
  • Deployment: Knative on Kubernetes (on-prem or any cloud), 9/9 smoke checks, scale to zero.

Pitches

30 seconds

"I built Yatra Pulse, a travel board for Mysuru Dasara with an AI trip planner that can't make things up. It retrieves only real events from the board, Claude drafts a plan from those, and a deterministic checker flags clashes and legs you can't travel in time.   2. Goal: a plan a traveller can actually follow: real, clash-free, reachable, cited.
  3. Approach: retrieve → generate within a whitelist → verify deterministically.
  4. Proof: evaluator numbers; trip check catches the real 17 Oct clash.
  5. Production thinking: MCP for reuse, Pulsar telemetry and SLOs, Knative deployment.
  6. What I learned: two bugs only metrics could find; one rollout bug only deployment could find.
03

Architecture walkthrough (whiteboard in five steps)

  1. Data: events, nightly shows, DJ nights, day trips and booking facts live in one shared block of index.html, each with a source URL and, for venues, coordinates.
  2. Board: plain HTML/CSS/JS renders the schedule every minute in IST; the itinerary saves to the claude.ai database or the browser.
  3. Agent: retrieve with BM25 → one Claude call with only retrieved keys → drop unknown keys → trip check → show problems and sources. The traveller decides.
  4. MCP: the same shared code runs in a Node MCP server (stdio for desktop, Streamable HTTP for the cluster) with search, day schedule, trip check and booking tools.
  5. Operate: each tool call → Pulsar yatra-telemetry → metrics consumer → Prometheus, SLOs, alerts; evaluator runs → yatra-eval; all deployed as Knative services.

Problems I solved (STAR stories)

Real issues from building this project. Each shows a different skill.

Metrics revealed a test that lied

Situation
MCP tests all passed.
Task
Wire metrics and check them against real traffic.
Action
Noticed 2 of 6 searches returned nothing; traced to "concert" vs passages saying "Type: music"; the test asserted "every result is on day 14", true for an empty list.
Result
Added category words to passages; test now requires a result; no evaluator regression. Skill: observability finds what tests miss.

Pulsar shared subscription split my metrics

Situation
Knative smoke test: telemetry counted 3 calls instead of 4.
Task
Explain the missing events.
Action
Found two consumers on one Shared subscription (laptop and cluster), then again during a rollout (old and new pods). Gave each consumer its own subscription and switched to Failover.
Result
9/9 checks; counts whole during rollouts. Skill: messaging semantics.

A connection that never failed

Situation
New metrics pod never became Ready after the subscription-type change.
Task
Find why reconnect logic didn't help.
Action
Reproduced from the host: the WebSocket upgrade stalled, firing neither open nor close, so backoff never ran. Added a 10 s connect timeout to producer and consumer.
Result
Consumers recover from stuck upgrades. Skill: failure modes beyond "error".

Knative couldn't find local images

Situation
Revisions stuck at RevisionMissing on kind.
Task
Deploy locally built images.
Action
Read the revision message: Knative resolves tags to digests on Docker Hub (401). Used dev.local/ names, which Knative skips, in a kind-only overlay.
Result
Same app manifests for laptop and cloud. Skill: reading platform behaviour.

Resource limits on a laptop cluster

Situation
Pulsar pod Pending: insufficient memory.
Task
Run the full stack on a 1.9 GB Docker VM.
Action
Split manifests into app and Pulsar; the laptop profile points at an existing Pulsar, exactly like a managed Pulsar in production.
Result
Deployment verified; the production path unchanged. Skill: designing for environments.

A video caught a mobile bug

Situation
The recorded phone scene showed a shrunken desktop layout.
Task
Fix the video.
Action
Realised the standalone page had no viewport meta (the artifact host adds one), so real phones on GitHub Pages would have broken too.
Result
Fixed the product, not just the video. Skill: treat every artefact as a test.

Grounding the AI planner

Situation
First planner sent the whole board and trusted the output.
Task
Make it impossible to invent events and cheap to run.
Action
Added retrieval, a key whitelist, tips only from facts, and trip check on the draft; built an evaluator for invented, clashing and wrong-day stops.

06

Practice questions

Say your answer out loud first, then open the model answer.

Product and goals

What problem does Yatra Pulse solve, and for whom?

Festival travellers in Mysuru during Dasara: a dense 11-day schedule across venues 5–15 km apart, ticket windows and gate deadlines. It shows what's on, builds a plan you can actually follow, and points to the official way to book. Secondary users: the host who curates traveller events, and developers who query it from Claude via MCP.

What is the agent's goal, and how do you know it's met?

"Plan a trip a traveller can actually follow": every stop real, nothing clashing, every leg reachable, gates respected, every stop cited. Measured by the evaluator's plan scorer (grounded 100%, invented 0, wrong-day 0), trip check on every draft (0 unflagged problems), and retrieval hit@1 ≥ 0.8 (0.97 today).

Why not just ask ChatGPT or Claude directly?

A general assistant doesn't know this year's schedule, invents plausible events, and doesn't compute travel time between venues. Yatra Pulse constrains generation to retrieved, sourced data and checks feasibility deterministically, so the answer is both current and followable.

AI, RAG and agents

Walk me through the RAG pipeline.

Each item becomes one passage with a key, day and URL (37 today). Query = style words + traveller note; BM25 (k1 1.4, b 0.75) ranks with day and kind filters; the planner takes 4 events per day, 3 nightly shows, 4 trips, 3 facts. Claude must answer with those keys; unknown keys are dropped; tips only from facts; the draft is trip-checked.

Why BM25 and not a vector database?

Small corpus of proper nouns where lexical match is strong; runs in the browser in under a millisecond with no model or network (the sandbox blocks network anyway); same results in page and MCP server. Measured: hit@1 0.97. I'd add embeddings in a hybrid when the corpus grows or queries become paraphrase-heavy; the known miss ("stars" → star-shaped temple) is exactly the kind of error hybrid ranking fixes.

How do you prevent hallucinations?

By construction rather than by prompting alone: whitelist of retrieved keys (anything else is dropped before display), tips only from retrieved facts, unannounced times never filled in, deterministic trip check, sources shown. The evaluator tests that invented stops are caught.

Why does the page planner use one Claude call instead of an agent loop?

Each tool round is another paid request and adds latency. With a small corpus, retrieving up front gives the model everything in one call; checks are deterministic code. The MCP concierge, where multi-step work is natural, does search → draft → check → revise.

What is MCP and why use it here?

Model Context Protocol: a standard way to give AI clients tools, resources and prompts. It lets Claude Code or Desktop use the same search and trip check as the board, so answers are grounded outside the web page too. I serve it over stdio for desktop clients and Streamable HTTP for Kubernetes.

Evaluation and testing

How do you evaluate the AI parts?

Labelled datasets: 31 retrieval questions (hit@1, recall@3, MRR@5), 10 trip-check scenarios with must and must-not statuses, 4 plans for the plan scorer, plus a latency gate. Thresholds in a file; CI fails below them; each run is published to Pulsar so the dashboard shows the latest score.

What's your testing strategy end to end?

Selenium for the real browser (16 checks), an MCP client over the real protocol (8), the evaluator for AI quality, a game day for alerting, and a smoke test against a live Knative deployment (9). CI runs MCP tests, the evaluator and image builds on every push.

Tell me about a test that was wrong.

The "search with a day filter" MCP test asserted all results were on day 14; it passed with zero results. Metrics showed empty searches; I fixed the data (category words) and the test now requires a result. Lesson: assertions over collections must also assert non-empty.

Observability and operations

Why Apache Pulsar for telemetry?

Durable topics decouple producers from consumers, subscriptions let new consumers replay, and a dead-letter topic isolates bad data. The WebSocket API avoided native client libraries in the images. Kafka would also work; Pulsar's subscription types (Failover) solved my rollout problem neatly.

What are your SLOs and why those?

≥ 99% tool calls succeed (a failure means Claude answers without the board), p95 ≤ 250 ms (tools run inside a conversation), ≥ 90% searches non-empty (empty pushes Claude to answer from memory), and evaluator passing (quality). 15-minute window with minimum data before breach; alerts fire once and resolve once.

How do you make sure telemetry doesn't take the service down?

Fire-and-forget sends, a short in-memory buffer at startup, file fallback when Pulsar is unreachable, describe-function errors swallowed, logs on stderr (stdout is the MCP protocol), connect timeouts and backoff. A tool call never waits on the broker.

Shared vs Failover vs Key_Shared subscriptions?

Shared: messages round-robin across consumers (scale out, but each sees a subset). Failover: one active consumer, others standby (order and whole counts). Key_Shared: per-key ordering across consumers. My metrics consumer needs whole counts, so Failover; I learnt this when a Knative rollout overlapped two consumers.

Kubernetes and Knative

Why Knative rather than plain Deployments?

Scale to zero for idle services, request-based autoscaling, immutable revisions and traffic splitting out of the box, and the same manifests on any cluster. Verified: web and MCP scaled to zero after 4 idle minutes; 2.2 s cold start.

Why is the metrics consumer pinned to one replica?

It holds the SLO window in memory and must stay subscribed to receive telemetry; scale-to-zero would drop events and windows. With Failover subscriptions, overlapping pods during rollouts are safe.

How would you run this on-prem vs in the cloud?

Same Knative manifests. On-prem: k3s/RKE2/OpenShift with the Knative Operator or OpenShift Serverless, Pulsar via Helm on local storage. Cloud: GKE/EKS/AKS with Knative, Pulsar via Helm or a managed service; point PULSAR_WS_URL at it. Images in any registry via kustomize.

Walk me through the AWS architecture.

Terraform builds a two-AZ VPC (public subnets for ALB and one NAT, private for nodes), EKS 1.35 with a managed node group and EBS CSI via Pod Identity, three ECR repos, an ALB with a NodePort target group, and CloudFront in front. Knative and Kourier (ClusterIP) are installed by script; an nginx gateway maps /, /mcp and /ops/ to the Knative services. EventBridge Scheduler stops the nodes overnight. Verified with 16/16 recorded browser scenarios and 8/8 API checks, then torn down with a leftover sweep.

Why not ECS Fargate on AWS?

Fargate would be simpler for one service, but Knative keeps one set of manifests for laptop, on-prem and AWS, and gives scale-to-zero and revisions. The cost is running EKS; I'd pick Fargate or App Runner if portability didn't matter.

How do you make sure teardown leaves nothing billable?

Delete the namespace first so the EBS CSI driver deletes Pulsar's volume (Terraform doesn't track it), run terraform destroy, then sweep for EKS, load balancers, CloudFront, NAT, EIPs, EBS, instances, VPC and ECR, and write the result to a report. No KMS key, because deleted keys linger 7+ days.

How did you secure the containers?

Non-root images, runAsNonRoot with explicit UIDs, no privilege escalation, all capabilities dropped, RuntimeDefault seccomp, memory limits, read-only tools, no secrets in config.

Scaling and trade-offs

What breaks first at 100× traffic?

The metrics consumer (single, in-memory) and per-call BM25 index rebuilds. Fixes: cache the index, partition telemetry and aggregate per partition or move aggregation to Prometheus, run Pulsar via its Helm chart, raise MCP max-scale.

What would you change if you started again?

Put data in a small JSON store with a schema from day one instead of inside the HTML, design subscription types up front, add a connect timeout to every network client by default, and add a property-based test for trip check across random itineraries.

Limits and next steps (say these before they ask)

  • Event data is curated by hand (last checked 11 Oct 2026); next: a scheduled job that proposes updates for the host to approve.
  • Travel times are estimates from approximate coordinates; next: a routing service with live traffic where network is allowed.
  • Trip check compares neighbouring stops; next: full interval checks and property-based tests.
  • Lexical retrieval with one known miss; next: hybrid BM25 + embeddings when the corpus grows.
  • Single-node Pulsar on the laptop; production uses the Pulsar Helm chart or a managed service.
  • The page planner flags but doesn't revise; next: an opt-in "fix it" round.

How it was built

This project was built in one session with Claude Code as an AI pair-programmer: the decisions above were discussed and chosen in that session, and every part was run and verified (tests, evaluator, deployment) rather than only written. In an interview, say so plainly, and show that you understand each decision and can change it. Good preparation: re-run node eval/run.js, ./deploy/local/smoke-test.sh and the Selenium suite yourself, and be ready to explain the trip-check formula and the Failover fix from memory.
