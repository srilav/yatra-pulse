Yatra Pulse architecture

A live travel board for Mysuru Dasara 2026, an MCP server that lets Claude answer from it, an evaluator that keeps its AI honest, telemetry on Apache Pulsar, and a Knative deployment that runs on any Kubernetes, on-prem or in the cloud.

04

AI-enabled components

Every AI path is grounded in the board and checked by deterministic code before a traveller sees it.

RetrieveEvents · shows · DJ · trips · facts · traveller events→boardPassages()→searchBoard() BM25
GeneratePlan with Claude (sample.json)orClaude via MCP tools
GuardKeep retrieved keys only→Trip check the draft→Show sources
MeasureEvaluator datasets→Quality gates in CI→yatra-eval
AI · RAG

Board search

BM25 over every passage, with category and style words. Hit@1 0.97, recall@3 1.0 on 31 labelled questions; p95 under 1 ms.

AI · generation

Plan with Claude

Retrieves up to 4 events per day, 3 nightly shows, 4 trips, 3 facts; one Claude call; drops unknown keys; tips only from facts.

AI · guardrail

Trip check

Deterministic check on every AI draft: clashes, travel time, gate deadlines, vehicle range. Problems shown in red before "Add all".

AI · tools

MCP server

search_board, get_day, check_itinerary, booking_guide, two resources and the plan_trip prompt for Claude Code and Desktop.

AI · evaluation

Evaluator

Scores retrieval, trip check (10 scenarios) and plan grounding (invented stops, clashes, wrong days) against thresholds.

Telemetry flowing to Pulsar

Every decision the server makes for a traveller becomes an event, and every event turns into metrics, SLOs and alerts.

ProduceMCP tool call→telemetry.span()→yatra-telemetry(Pulsar down →telemetry.jsonl)
Produceeval/run.js→yatra-eval
Consumemetrics consumer (Shared subscription)→/metrics · /stats · dashboard
AlertSLO check every 30 s→yatra-alerts· bad payloads →yatra-telemetry-dlq

Clients use Pulsar's WebSocket API with reconnect and backoff, so there are no native libraries to install. Search text isn't recorded unless TELEMETRY_INCLUDE_QUERIES=1. The runbook (ops/RUNBOOK.md) covers every alert.

# Build images (repo root)
docker build -f deploy/docker/web.Dockerfile     -t yatra-pulse/web:1.0.0 .
docker build -f deploy/docker/mcp.Dockerfile     -t yatra-pulse/mcp:1.0.0 .
docker build -f deploy/docker/metrics.Dockerfile -t yatra-pulse/metrics:1.0.0 .

# Push to your registry, set it in deploy/k8s/kustomization.yaml, then
kubectl apply -k deploy/k8s          # app + in-cluster Pulsar
# or: kubectl apply -k deploy/k8s/app   # app only, PULSAR_WS_URL → your Pulsar
# laptop: ./deploy/kind-up.sh && ./deploy/smoke-test.sh
kubectl get ksvc -n yatra-pulse

On the laptop, the deploy/kind profile loads images into kind and uses the Docker Compose Pulsar, because Knative alone fills a 2 GB Docker VM. Real clusters use kubectl apply -k deploy/k8s, which adds the Pulsar StatefulSet, or deploy/k8s/app with an existing Pulsar.
