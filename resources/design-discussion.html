Design discussion · how each feature is built

Yatra Pulse: component by component

For each part of Yatra Pulse, from the board to the agent, evaluator, telemetry and Knative deployment: what it's for, the code that implements it, the decisions we made and why, and the edge cases it handles. Function names refer to index.html; the MCP server lives in mcp-server/. The visual reference is the design guide (docs/design.html), and the requirements are in SPEC.md.

00

Architecture

The whole app is one HTML file with inline CSS and plain JavaScript. There is no framework and no build step. It runs as a claude.ai Artifact (which adds the database, identity and Claude features) and also opens straight from disk, where those features switch off gracefully.

Renderingrender() rebuilds each section with template strings every 60 s and after every change.
EventsOne delegated click listener on document handles every [data-add], [data-rm] and [data-book].
Shared codeData, itinerary, trip check and search sit between SHARED-START and SHARED-END; the MCP server runs that exact block.
Platform featuresdb (saved plans, traveller events), user (who's viewing), sample (Claude), each loaded with claude.use() and allowed to be null.

The script runs in this order:

SHARED-START
  T(), EVENTS, NIGHTLY, DJ, TRIPS, DAYS, formatters      // data + time helpers
  plan, catalogItem(), setPlan(), renderPlan()           // itinerary
  VENUES, MODES, resolveStop(), evaluateDay(), toast()   // trip check
  KNOWLEDGE, boardPassages(), searchBoard()              // RAG
SHARED-END
src(), state(), render(), bindChips()                    // page rendering
event listeners, setInterval(render, 60000)
async: db + user boot (traveller events, saved plan)
async: sample boot (Plan with Claude)
Decision: one file, no framework

The page has to publish as a single artifact, open from GitHub without tooling, and load fast on a phone at a crowded festival. About 20 events and a handful of panels don't need a virtual DOM; a full re-render takes milliseconds. The cost is that re-rendering replaces DOM nodes, so all handlers are delegated and form fields live outside re-rendered areas.

01

Time model

Everything is in India Standard Time, whatever the viewer's own clock says.

Build a time
  • T(day, "HH:MM") returns new Date("2026-10-DDTHH:MM:00+05:30"), so the offset is fixed in the string.
Display
  • fmtT, fmtD are Intl.DateTimeFormat with timeZone: "Asia/Kolkata". istDay() and istMonth() read the IST calendar day.
Occurrences
  • OCC expands data into dated occurrences: each event once, each nightly show once per festival day (11 × 3).
State
  • state(o, now): done after end; live between start and end (or today if the time is TBA); soon within 6 hours; else tba or up.
Decision: offsets in the data, not the viewer's time zone

A traveller planning from London or Bengaluru must see 4:10 pm for Jamboo Savari. Writing +05:30 into every time and formatting with Asia/Kolkata avoids any daylight-saving or locale surprises.

02

Theme and palace bulbs

Tokens
  • Every color is a CSS custom property on :root (bg, surface, ink, muted, line, gold, bulb, kumkum, live, tba). Dark values are redefined under prefers-color-scheme: dark and again under [data-theme="dark"], so the viewer's theme toggle wins in both directions.
Bulbs
  • A 10px strip whose background is a repeating radial-gradient dot; a two-step @keyframes opacity change makes it twinkle. Disabled under prefers-reduced-motion.
Type
  • Yatra One for display, Mukta for body, JetBrains Mono with tabular-nums for times and prices so columns line up.
Decision: semantic colors separate from the accent

Marigold is the brand accent; green, amber and red are reserved for status (live / to watch / problem). Status is always also said in words or shown with a shape (!, ~, ↓), so color-blind travellers lose nothing.

Now & next

Selection

Card

After the festival

05

Timeline and filters

Structure
  • A nightly band (three items shown once with times), then one .day row per day 11–21. Today gets .today; past days .past.
Events
  • Each .ev[data-cat] shows pill, time or "Time TBA", venue, note, source, a "Book tickets" link where book is set, and the add button.
Filters
  • bindChips("f", …) wires the chips; the choice sets filter, re-renders, and is remembered in localStorage["mm-f"]. Filtering compares o.cat (ritual, music, dj, show).
Empty days
  • A filtered day with nothing says so ("Nothing in this category today") rather than disappearing, so the 11-day rhythm stays visible.
06

Picks for you and DJ nights

Picks
  • Style chips set vibe. Picks are the first three upcoming events whose tags include it (one per title), plus two day trips with the same tag.
DJ nights
  • A curated DJ list with sources, plus a plain note that no Mysuru club nights are announced. Sandalwood Nights and Jasmine Sandlas carry cat: "dj" so the DJ filter finds them in the timeline too.
Decision: tags, not a recommender

Four styles and about 20 items make hand-chosen tags more predictable than any learned ranking, and travellers can see why something was picked.

07

My itinerary

Model
  • plan is an array of {key, day, title, time, place, url}. Keys identify the source item: ev:21:Jamboo Savari, nt:Palace illumination, trip:Melukote, cm:<id>. Items added by Plan with Claude get @day on non-dated keys so the same trip can appear on two days.
Adding
  • togglePlan(key) → catalogItem(key) builds the entry from the board data (day trips and nightly shows take the day picker's value) → setPlan() → trip check for that stop → toast.
Saving
  • savePlan() always writes localStorage["mm-plan"], and when signed in also writes data/users/<id>/plan after a 700 ms debounce (one write per burst of taps).
Loading
  • The page shows the browser copy immediately. When the database answers, the first snapshot decides: if the account has a plan, it wins; if not, the browser plan is uploaded. Later snapshots (another device) replace the plan unless they're our own pending write.
Rendering
  • renderPlan() runs evaluatePlan() and interleaves trip-check legs between stops, adds day notes, and fills the summary pills.
Copy and clear
  • planText() builds plain text for WhatsApp; navigator.clipboard.writeText inside the click, with a "select it by hand" fallback. Clear needs a second tap within 3 s, because artifacts can't show confirm dialogs.
Decision: store a snapshot of each stop, resolve details at check time

Saved items keep title, place and URL so the plan still reads well if the board data changes. Trip check, however, looks the key up again in resolveStop(), so it always uses current times and venues.

08

Trip check

The evaluator that stops a traveller booking two places at once, or a plan they can't physically follow.

Resolve
  • resolveStop(entry, mode) returns start, end, mustBy (gate close via arriveBy, else start), venue coordinates from VENUES, and flags: tba, crowd, flexible (nightly shows). Day trips get end = leave + 2 × drive + visit (2 h, or 3 h for trips over 60 km), measured from the palace.
Distance
  • roadKm() is haversine distance × 1.4. driveMin() charges the first 15 km at the vehicle's city speed and the rest at highway speed, plus the vehicle's wait.
Compare
  • evaluateDay() sorts timed stops by mustBy and compares each neighbour pair: gap = next.mustBy − prev.end; travel = drive + 25 min (crowded venue) or 10. Clash if gap < 0 at different venues (> 0.8 km); "warn" instead if one side is a flexible nightly show, with a "leave by" time; not enough time if gap < travel; tight if gap < travel + 15; otherwise OK with km, minutes and a Google Maps route link.
Notes
  • Per-stop notes: time not announced, no map location (traveller events), auto-rickshaw beyond 40 km, and the Jamboo Savari gate deadline.
Where it runs
  • Itinerary render, checkStop() on add and on "Book tickets", the Plan with Claude draft, and the MCP check_itinerary tool. One function, five callers.
travel  = cityKm / city + highwayKm / road (h → min) + wait + (crowded ? 25 : 10)
gap     = next.mustBy − prev.end
status  = gap < 0 && differentVenue ? "Clash"
        : gap < travel               ? "Not enough time"
        : gap < travel + 15          ? "Tight"
        :                              "OK"
Decision: local estimates instead of a maps API

The artifact sandbox blocks network calls to other sites, and a maps API would need keys and cost per request. Approximate coordinates with conservative festival speeds give the right answer for the decisions that matter (Bannimantap vs Uttanahalli in 60 minutes), and every leg links Google Maps for live traffic on the day.

Known limit: only neighbouring stops are compared, after sorting. Three overlapping stops produce two clash rows, which is enough to flag the day. Coordinates are approximate; drone show and palace-viewing end times are estimates and say so in the SPEC.

09

Board search (RAG)

Passages
  • boardPassages() turns every event, nightly show, DJ night, day trip, approved traveller event and KNOWLEDGE fact into {key, kind, day, title, text, url}. The text spells out the day, time, venue, note, category and tags so they're searchable.
Tokenizer
  • Lower-case, strip accents (NFKD), split on non-alphanumerics, drop stop words, drop a trailing "s" on words over three letters.
Ranking
  • searchBoard(query, {day, kinds, k}) filters by kind and day (undated passages always pass), then scores with BM25: k1 = 1.4, b = 0.75, idf = ln(1 + (N − df + 0.5)/(df + 0.5)). Ties go to the earlier day.
Query expansion
  • STYLE_WORDS adds words for the chosen style, e.g. spiritual → temple, puja, ritual, goddess, spiritual, blessing.
Decision: BM25 in the page, not embeddings

About 40 short passages, full of proper nouns (Sid Sriram, Bannimantap, Gold Card), are exactly where keyword ranking is strong. It runs in under a millisecond with no model download, needs no network (which the sandbox would block anyway), and gives identical results in the page and the MCP server. If the corpus grew to thousands of reviews, a hybrid of BM25 and embeddings would be the next step.

10

Plan with Claude

Retrieve
  • choices() builds a query from style words and the traveller's note, then retrieves up to 4 events per day (events and traveller events), 3 nightly shows, 4 day trips and 3 facts.
Generate
  • One sample.json() call (default model tier, abortable with Stop). The prompt sets rules: only use keys from CHOICES, respect days and times, no two venues at once, tips only from FACTS, and a fixed JSON shape.
Validate
  • Days outside the stay are dropped; stops whose key wasn't retrieved are dropped; at most 6 per day. Free-time suggestions (key null) are shown in italics and never added.
Check
  • The draft goes through evaluateDay() with the chosen vehicle; problems are listed in red above "Add all to my plan".
Errors
  • Codes map to plain messages: cancelled, not_granted (allow it in Permissions), rate_limited (wait a minute), anything else (try again or add stops by hand). No automatic retries.
Off claude.ai
  • claude.use("sample") is null, so the button is disabled with an explanation.
Decision: retrieve-then-generate, not tool calls

The platform supports letting Claude call page functions, but each round is another paid request that takes longer. The corpus is small enough to retrieve up front in one step, so the plan arrives in a single call, and the key whitelist guarantees no invented events. The MCP server is where the tool-calling style is used, because desktop clients do multi-step work well.

11

Agent goal and loop

Both AI paths serve one goal (SPEC §6): plan a Dasara trip a traveller can actually follow. Every stop real, nothing clashing, every leg reachable by the chosen vehicle, gate deadlines respected, every stop cited.

Two agents
  • Trip planner (the board): retrieve once, one sample.json() call, deterministic checks. Dasara concierge (Claude Code / Desktop over MCP): multi-step tool use guided by the plan_trip prompt.
Loop
  • Retrieve → draft with retrieved keys only → trip check → revise (concierge) or flag in red (planner) → present with sources; the traveller decides what to add.
Success measures
  • Grounded 100%, invented 0, unflagged problems 0, wrong-day 0 (all computed by scorePlan() in the evaluator); retrieval hit@1 ≥ 0.80; one Claude call per page plan.
Permissions
  • Read-only tools. The agent never books, pays, writes traveller events or reads other people's data; writing the plan needs the traveller's tap.
Decision: the page planner flags, it doesn't auto-revise

A revise round would be a second paid Claude call and roughly double the wait. Showing problems in red keeps the traveller in control at a fixed cost. The MCP concierge, where multi-step work is natural, is told to fix and re-check.

12

Traveller events

Storage
  • tips/<userId> holds one person's submissions as {items: [...]}: private to them and the host. approved/<tipId> holds what the host approved: readable by everyone.
Access rules
  • Root: read view, write admin. tips: read admin, write owner. tips/{self}: read and write interact (Contributor). Viewers can browse but not submit; only the owner can change someone else's status.
Checks
  • validate() runs before anything else: name ≥ 4 chars; https only; real hostname; no link shorteners (bit.ly and 9 others); date 11–31 Oct 2026; venue; write-up 40–400 chars; "this is real" ticked; link not already added; at most 5 waiting per person. Only then does it check sign-in.
Review
  • The owner subscribes to the whole tips collection. setStatus() reads the submitter's doc, writes approved/<id> (or deletes it on reject), then updates the status in their list.
Display
  • Names are resolved at render time with user.profiles(ids); only opaque ids are stored, never names.
Decision: host approval instead of automatic checks

A page can't confirm that an event exists. The form rules raise the bar (full official links, a real description, a declaration) and the human check does the rest. That is why nothing is public until approved.

How to book

Content
  • Static HTML: five numbered steps (check itinerary → official site → pay → collect at Spandhana Counter with ID → on the day), a price table, helpline 1077 and getting-there tips. The same facts are in KNOWLEDGE for search and MCP.
Book tickets links
  • Ticketed events carry book; their link has data-book. The delegated click runs checkStop() and shows the result before the browser opens the official site. It never blocks the link.
Layout
  • Numbered circles come from a CSS counter on .steps; the price table scrolls inside .tablewrap on phones.
Decision: never sell, always point to the official seller

The board shows totals as reported, names TicketGenie as the only authorised seller, and links mysoredasara.gov.in. It never handles payment, which keeps it out of the scam problem it warns about.

Day trips and Gaya

Day trips

Gaya panel

15

MCP server

Loading
  • board.js reads ../index.html, slices the SHARED block, and runs it in a Node vm context with a stub document. A trailing expression returns the data and functions.
Tools
  • search_board (BM25 passages with URLs), get_day, check_itinerary (calls evaluateDay), booking_guide. Inputs are zod schemas; all tools are read-only.
Resources and prompt
  • yatra://schedule (Markdown), yatra://facts (JSON), and plan_trip, which tells Claude to search, draft, check and fix, then cite sources.
Transport
  • stdio (server.js) for Claude Code (.mcp.json) and Claude Desktop; Streamable HTTP (http.js) for containers and Knative. Both build the same server from app.js, and every tool call is traced to Pulsar.
Decision: execute the page's code instead of exporting JSON

A JSON export would copy the data but not the trip-check rules or the ranking, and the copies would drift. Running the shared block keeps one source of truth. The SHARED-START comment warns that nothing in that block may touch the DOM at load time.

16

Evaluator

Datasets
  • eval/datasets/retrieval.json: 31 traveller questions with the passages that answer them. tripcheck.json: 10 itineraries with the statuses trip check must (and must not) give. plans.json: 4 AI-shaped plans with the verdict the plan scorer must reach.
Scores
  • Retrieval hit@1, recall@3, MRR@5; trip-check accuracy; plan-evaluator accuracy; search p50/p95 over 2,000 queries.
Gates
  • eval/thresholds.json; exit code 1 below any gate, so CI fails. Each run is written to eval/results/latest.json and published to Pulsar yatra-eval.
Reuse
  • Loads the same shared code as the MCP server (board.js), so it scores exactly what ships.
Decision: label behaviour, not just answers

Trip-check cases list statuses that must appear and statuses that must not, so a change that adds a false "Clash" fails as surely as one that misses a real one. Plans are scored on grounding, invention, clashes and wrong days, the four ways an AI plan can mislead a traveller.

What it caught: the metrics showed "concert" searches returning nothing; the MCP test for it was passing on an empty list. Fix: category words (CAT_WORDS) in passages, and the test now requires a result. One known miss remains and is reported on every run ("stars" ranks the star-shaped Somanathapura temple first).

17

Telemetry to Apache Pulsar

Client
  • ops/pulsar.js talks to Pulsar's WebSocket API with Node's built-in WebSocket: producer with acks and reconnect (0.5 s → 30 s backoff) and a 10 s connect timeout (a stalled WebSocket upgrade once hung a consumer forever); consumer with ack, negative-ack and poison handling.
Events
  • telemetry.span(tool, fn) wraps each MCP tool: one tool_call event with trace id, ok/error, latency and domain results (results, zero_result, top_score; problems, clashes; events). Plus server_start and server_stop.
Never hurts the service
  • Fire-and-forget; events from the first 5 s wait in memory for the connection; when Pulsar is unreachable they go to ops/telemetry.jsonl; a failing describe function is ignored. Logs are JSON on stderr because stdout carries the MCP protocol.
Privacy
  • Search text is replaced by a hash and length unless TELEMETRY_INCLUDE_QUERIES=1.
Decision: Pulsar's WebSocket API instead of a native client

The official Node client needs a C++ library on every machine and container. The WebSocket API ships with Pulsar, works from any runtime with a WebSocket, and keeps the images small and dependency-free.

18

Metrics, SLOs and alerts

Consumer
  • ops/metrics-consumer.js subscribes to yatra-telemetry and yatra-eval with a Failover subscription (one active consumer; a Shared one split counts between overlapping pods during a Knative rollout), keeps counters, latency histograms (5 ms to 2.5 s buckets) and a 15-minute window.
Outputs
  • /metrics (Prometheus), /healthz, /stats, and a dashboard that polls /stats every 5 s.
SLOs
  • Tool calls ≥ 99% successful; p95 ≤ 250 ms; ≥ 90% of searches non-empty; latest evaluator run passing. Each needs a minimum of data before it can breach.
Alerts
  • One firing event on breach and one resolved on recovery, published to yatra-alerts; unparseable messages go to yatra-telemetry-dlq. The same rules exist as Prometheus alerts and a PrometheusRule.
Game day
  • ops/simulate.js injects errors, slow calls, empty searches and poison messages; on 11 Oct it fired the availability alert at 82.8% and routed the poison message to the DLQ.
Decision: SLOs computed by the consumer itself

Alerts work with no Prometheus at all (laptop, small on-prem), and the identical rules in ops/alerts.yml take over where Prometheus exists.

19

Deployment on Knative

HTTP MCP
  • mcp-server/app.js builds the server; server.js runs it over stdio, http.js over Streamable HTTP. Stateless: a fresh server and transport per request, /healthz, /readyz, and SIGTERM drains telemetry before exit.
Images
  • nginx-unprivileged for the web board and docs; Node 22 Alpine for MCP and metrics; all non-root.
Services
  • yatra-web 0–5 pods, yatra-mcp 0–10 (target 50 concurrent, 2 min scale-down delay), yatra-metrics exactly 1. Pulsar as a StatefulSet, or an existing cluster via PULSAR_WS_URL.
Profiles
  • deploy/k8s for real clusters; deploy/local/kind for laptops (dev.local images, Docker Compose Pulsar).
Verified
  • kind + Knative 1.23: 9/9 smoke checks including telemetry MCP → Pulsar → metrics; web and MCP scaled to zero after 4 idle minutes; 2.2 s cold start.
Decision: stateless MCP, stateful metrics

Statelessness lets Knative scale the MCP server from zero to ten and back with no session affinity. The metrics consumer holds its SLO window in memory and must stay subscribed, so it is pinned to one replica rather than given scale-to-zero.

Found while deploying: Knative tried to resolve local image tags on Docker Hub (fixed with dev.local names), and Pulsar couldn't be scheduled next to Knative in a 1.9 GB Docker VM (laptop profile uses the Compose Pulsar; real clusters keep the StatefulSet).

Safety and honesty

ConcernHow it's handled
Script injection from traveller textEvery value written into HTML goes through esc(); links render only if they start with https://.
Malformed database rowsDates are parsed inside try; sorting coerces to strings; unknown keys are skipped.
Invented events from AIWhitelisted keys only; tips only from retrieved facts; trip check on the draft.
Unannounced timesShown as "Time TBA", never guessed; trip check marks them "to watch".
Fake listingsForm rules plus mandatory host approval.
Scam ticket sellersOfficial site only; "no agents" stated in the booking steps.
Private dataPlans live in a per-person database path; only ids are stored for traveller events.
