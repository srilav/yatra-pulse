The look

The idea is Mysuru Palace on a Dasara night: deep night-sky purple, marigold bulb light, and kumkum red for things that need attention. The light theme keeps the same accents on a soft lilac-white. Every color is a token on :root, redefined for dark mode, so components never use raw colors.

Source link and add button

  • .srclink always shows the website's name next to the link, so people can judge the source before clicking. Only https links are shown.
  • "Book tickets" links carry data-book; clicking one runs Trip check first and shows the result in the toast.
  • .addbtn[data-add] toggles the stop in the itinerary. aria-pressed holds the state; dashed outline when off, filled when on.

Chips and buttons

  • .chipbtn for filters and travel styles; the selected one has aria-pressed="true" and inverts. The choice is remembered in this browser.
  • .btn is the main action in a panel; .btn.ghost for secondary actions.
  • "Clear" asks for a second tap instead of a pop-up, because the viewer can't show confirm dialogs.

How Trip check decides

For each day, stops are sorted by the time you must be there (gate closing time if the ticket has one, otherwise the start). Each pair of back-to-back stops is compared.

ResultRule
ClashThe earlier stop ends after the next must start, and they're at different venues (more than 0.8 km apart). If one of them is an all-evening item like palace lights, it's a warning with a "leave by" time instead.
Not enough timeGap < travel time. Travel = road km ÷ speed + waiting, plus 25 min for parking and entry at crowded venues or 10 min elsewhere.
TightGap is less than travel time + 15 minutes.
Too farAn auto-rickshaw on a day trip over 40 km.
To watchTime not announced, no map location (traveller events), or a gate deadline such as Jamboo Savari's 12:30 pm.
OKSame venue, or the gap covers travel with time to spare.

Road distance is straight-line distance × 1.4. The first 15 km count as city driving. These are planning estimates; each leg links a Google Maps route for live traffic.

Event keys look like ev:21:Jamboo Savari, nt:Palace illumination, trip:Melukote and cm:<id>. Plan with Claude must answer with these keys, which is how the page drops anything it didn't get from the board.

RAG and MCP

Claude only ever plans from what the board knows. The board splits itself into short passages, each with a key and a source link, and ranks them with BM25 for the traveller's question. The same code runs in the page and in the MCP server.

Plan with Claude output

  • Retrieval sends up to 4 events per day, 3 nightly shows, 4 day trips and 3 facts. Claude must answer with their keys; anything else is dropped.
  • Tips may only come from the retrieved facts. The sources read are listed under the plan.
  • The draft goes through Trip check before "Add all to my plan", and any problem is listed in red.

MCP server

  • mcp-server/server.js loads the shared code from index.html between the SHARED-START and SHARED-END markers, so data and rules never drift.
  • Tools: search_board (RAG), get_day, check_itinerary, booking_guide. Resources: yatra://schedule, yatra://facts. Prompt: plan_trip.
  • All tools are read-only. See SPEC.md for setup in Claude Code and Claude Desktop.

Accessibility and behaviour

  • Status is always shown with words or a shape as well as color.
  • Toggle buttons use aria-pressed; messages use role="status".
  • Keyboard focus shows a marigold outline. Animations stop when reduced motion is on.
  • Light and dark themes follow the device, from the same tokens.
  • Phone width: two-column areas stack under 900px; tables scroll inside their own box.
  • No pop-up dialogs: confirmations happen in the page, such as Clear asking for a second tap.
